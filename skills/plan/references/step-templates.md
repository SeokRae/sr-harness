# 작업 유형별 단계 틀

계획을 쓸 때 작업 유형에 맞는 틀 하나를 단계의 뼈대로 쓴다. 맞는 틀이 없으면 틀 없이 쓴다.

모든 틀은 같은 규칙을 따른다.

- 1단계는 변경 전 기준을 고정한다. 기준은 다시 돌릴 수 있는 명령, 테스트, 출력이다.
- 마지막 단계는 1단계와 같은 곳에서 같은 방법으로 다시 확인한다.

## 버그 수정

1. 재현을 고정한다. 실패하는 재현 테스트를 쓰고 실패 출력을 남긴다.
   verify: 테스트 명령이 실패하고, 실패 내용이 보고된 증상과 같다
2. 원인을 좁힌다. 가설을 적고, 실행 증거(로그, 출력)로 하나만 남긴다.
   verify: 남은 가설 하나와 그 증거
3. 고친다.
   verify: 1단계 테스트가 통과한다
4. 증상이 보고된 곳(같은 명령, 같은 화면, 같은 입력)에서 다시 확인한다.
   verify: 1단계와 같은 확인의 통과 출력

커밋 순서: 1단계 재현 테스트 커밋이 수정 커밋보다 앞에 온다.

## 기능

1. 완료 조건을 실행할 수 있는 형태로 고정한다. 성공 기준을 테스트나 확인 명령으로 먼저 쓴다. 이 시점에는 실패한다.
   verify: 실패 출력
2. 구현 단계. 단계마다 verify에 실행할 명령이나 볼 화면을 적는다.
3. 1단계 확인을 다시 돌린다.
   verify: 1단계와 같은 확인의 통과 출력

## 리팩터링

1. 현재 동작을 고정한다. 특성 테스트, 스냅샷, 입출력 비교 스크립트 중 하나를 쓴다. 타입 검사와 lint는 동작 고정이 아니다.
   verify: 고정 수단이 지금 코드에서 통과한다
2. 구조를 옮긴다. 단계마다 1단계 고정 수단을 통과시킨다.
3. 1단계 고정 수단을 다시 돌린다.
   verify: 통과 출력

동작이 바뀌어야 하는 것을 발견하면 이 계획에 넣지 않는다. 기능이나 버그 수정으로 따로 나눈다.

## 문서와 노트

1. 변경 전 상태를 고정한다. 프로젝트 검사(노트 린터, 링크 검사, 문서 빌드)를 지금 상태에서 돌려 기존 오류를 남긴다. 다른 자료를 옮겨 적는 작업이면 원 출처(코드 위치, 원문 경로)를 적는다.
   verify: 검사 출력과 원 출처 목록
2. 작성 단계.
3. 1단계 검사를 다시 돌린다. 옮겨 적은 사실은 원 출처와 대조한다.
   verify: 새 오류가 없는 검사 출력, 대조한 항목 목록
