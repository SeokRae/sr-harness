# plan

"계획을 세운다"는 것은 곧 **Claude Code 내장 Plan Mode를 쓴다**는 뜻이다.
plan 스킬은 별도의 텍스트 형식 지시가 아니라, Plan Mode를 이 하네스의 계획 단계로 채택한 것이다 —
파일 편집 차단·조사 강제·승인 게이트를 sr-harness가 다시 구현하지 않고 Plan Mode의 툴 레벨 보장을 그대로 쓴다.

## 진입

이미 Plan Mode가 활성 상태(시스템이 알려줌)면 바로 아래 "계획 수립 형식"으로 넘어간다.
아직 아니면 `EnterPlanMode`로 진입한 뒤 시작한다. `brainstorm`을 이미 거쳤다면 조사 단계는 그 결과를 재사용하고 새로 반복하지 않는다.

계획의 각 단계는 반드시 검증 가능한 완료 조건을 포함한다.
단계는 작게 — 하나의 단계가 하나의 논리적 변경 단위를 넘지 않는다.

## PRD 작성 — 항상 작성 (#101)

구현으로 이어지는 모든 작업은 규모·성격과 무관하게 계획 앞에 PRD를 둔다 — 버그 수정·리팩토링·한 줄
수정처럼 요구사항이 이미 명확해 보이는 작업도 예외 없이 포함한다. 과거 버전에 있던 "신규 기능이면
필요·버그수정이면 생략" 식의 작업별 판단은 하지 않는다.

이 게이트는 실제 구현(plan/execute로 코드·설정 변경이 이어지는 작업)에만 적용된다 — `start`의
라우팅 표에서 `plan`/`issue`/`execute`/`ralph`/`goal`로 이어지는 의도가 대상이며, 질문에 답하거나
방향을 상의하는 대화(예: brainstorm 이전 단계, 순수 설명·의견 요청)는 대상이 아니다.

## PRD 형식 (계획 파일 맨 앞에 항상 배치)

```
## 📄 PRD

### 배경 / 문제
{왜 이 작업이 필요한가 — 지금 무엇이 고통스러운가}

### 요구사항
- {요구사항 1}
- {요구사항 2}

### 범위 / 비범위
- 포함: {...}
- 제외: {...}

### 성공 지표
- {완료 후 확인할 수 있는 정량적/정성적 지표}
```

아래 "단계별 상세"는 이 PRD의 요구사항을 만족시키는 "어떻게"만 다룬다 — PRD 내용을 단계 설명에서 반복하지 않는다.
대상 프로젝트가 자체 PRD 문서 컨벤션(예: `docs/prd-*.md`)을 이미 쓰고 있다면, Issue 생성 시 이 섹션을 그 컨벤션에 맞는
별도 파일로도 남길지 사용자에게 확인한다(강제하지 않음).

## 계획 수립 형식

Plan Mode의 최종 계획 파일(`~/.claude/plans/{slug}.md`)에 아래 형식으로 쓴다(PRD 작성 시 위 섹션 다음에 이어붙인다):

```
## 🎯 목표
{한 문장: 무엇을 만드는가}

---

## ✅ 성공 기준
- [ ] {전체 완료 시 확인할 수 있는 것 1}
- [ ] {전체 완료 시 확인할 수 있는 것 2}

---

## 📋 단계 요약

| Step | 제목 | 규모 |
|------|------|------|
| 1 | {제목} | S/M/L |
| 2 | {제목} | S/M/L |

---

## 📝 단계별 상세

---

### Step 1: {제목}

**할 일:** {구체적 변경 내용}

> 🔍 verify: {이 단계가 완료됐는지 확인하는 방법}

---

### Step 2: {제목}

**할 일:** {구체적 변경 내용}

> 🔍 verify: {확인 방법}

---
```

## karpathy §4 내장 규칙

각 단계 작성 전에 확인:
- "Add validation" → "Write tests for invalid input, make them pass" 형태로 변환
- "Fix bug" → "Write a reproducing test, make it pass" 형태로 변환
- verify 없는 단계는 계획에 포함하지 않는다

## 승인 — ExitPlanMode가 그 자체로 승인 신호다

계획 작성이 끝나면 `ExitPlanMode`를 호출한다. 이것이 sr-harness가 항상 요구해온 "사용자 확인"이다 —
별도로 다시 "계획이 괜찮은지" 텍스트로 묻지 않는다(중복 확인).

- `ExitPlanMode`가 승인을 반환하면 → 바로 이어서 `issue` 호출 (Issue 생성 + 브랜치 생성). 계획 단계와 Issue 생성 사이에 다른 확인을 끼워 넣지 않는다.
- 사용자가 반려하면 → 피드백 반영 후 계획을 고쳐 다시 `ExitPlanMode`.

## session-plan.md — 별도 산출물이 아니라 같은 세트

계획 원본은 Plan Mode가 관리하는 `~/.claude/plans/{slug}.md` 하나뿐이다. `.claude/session-plan.md`를
사후에 "번역"해서 만드는 게 아니라, **계획이 승인되는 순간 그 요약을 함께 쓰는 것**으로 취급한다
(ExitPlanMode 직후, issue 호출 전에):

```yaml
---
session: YYYY-MM-DD
goal: {목표 — 계획 파일의 🎯 목표와 동일}
plan_file: ~/.claude/plans/{slug}.md   # 원본 위치, 상세는 여기서 확인
scope:
  - {단계 목록 — 계획 파일의 단계 요약과 동일}
---
```

`start`가 세션 재개 시 읽는 것은 이 요약이고, 전체 내용이 필요하면 `plan_file`을 연다.
