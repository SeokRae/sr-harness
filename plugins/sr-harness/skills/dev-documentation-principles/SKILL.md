# dev-documentation-principles

문서를 작성하거나 수정하기 전, 각 섹션의 원칙을 확인하고 반영한다.

> **활성화 방법**: 프로젝트 `CLAUDE.md`에 아래 한 줄을 추가하거나, 문서를 작성·수정하는 태스크 또는 되돌리기 어려운 설계 결정을 포함하는 태스크에서 로드한다.
> ```
> execute 실행 시 `dev-documentation-principles` 스킬을 로드하고 문서화 원칙을 구현에 적용한다.
> ```
>
> **적용 대상**: PRD/SPEC/ADR/README 등 문서를 새로 쓰거나 고치는 작업, 아키텍처·데이터모델·외부 연동 방식처럼 되돌리기 어려운 결정이 포함된 작업, 기존 문서와 코드가 어긋난 걸 발견한 작업.

## §1 결정 기록 (Decision Recording)

**목표**: 되돌리기 어려운 결정의 "왜"가 코드에도 미래 세션에도 흔적을 남긴다.

- **되돌리기 어려운 결정은 반드시 기록**: 아키텍처 선택, 데이터모델 변경, 외부 연동 방식, 마이그레이션 전략처럼 나중에 뒤집기 비싼 결정을 내리면 근거를 남긴다.
- **기록 위치는 프로젝트 컨벤션 우선**: `docs/adr/`, `specs/00-DECISIONS.md` 등 프로젝트가 이미 쓰는 위치가 있으면 그곳에 남긴다. 없으면 이슈/PR 설명에라도 "왜 이 방식을 선택했는지"를 남긴다.
- **"그냥 이렇게 했다" 금지**: 대안을 검토했는지, 왜 기각했는지가 드러나야 한다.
  - `트랜잭션 경계를 서비스 계층에 둔 이유: 레포지토리 계층은 여러 서비스에서 공유돼 경계가 새기 쉽다` ✅ / `트랜잭션은 서비스 계층에 둔다` ❌ (이유 없음)

## §2 문서-코드 드리프트 처리 (Drift Handling)

**목표**: 문서의 주장과 실제 코드가 어긋난 걸 발견했을 때 조용히 넘어가지 않는다.

- **발견 즉시 판정**: 기존 문서(스펙·설계 문서·README 등)의 서술이 실제 구현과 다르면, 어느 쪽이 맞는지 판정한다 — 대개 코드가 정본이지만, 코드 자체가 결함이면 "as-is 사실"과 "그 결함을 계속 따를지"를 분리해서 판단한다.
- **판정을 기록한다**: 문서를 코드에 맞게 고치거나, 프로젝트의 드리프트 기록 위치(예: `00-DECISIONS.md` 형식의 "문서 주장 / 코드 사실 / 판정" 표)에 남긴다.
- **침묵 금지**: 판정 없이 문서와 다른 코드를 그대로 두거나, 코드와 다른 문서를 그대로 방치하지 않는다.

## §3 기존 컨벤션 우선 (Existing Convention First)

**목표**: 프로젝트마다 다른 문서 체계를 존중하고, 새 체계를 임의로 얹지 않는다.

- **프로젝트 컨벤션을 먼저 찾는다**: PRD/SPEC/ADR/README 구조, 커밋 접두사(`docs:` 등), 소유권 표(어느 문서가 상류 정본인지) 같은 기존 규칙이 있으면 그 형식·위치·네이밍을 그대로 따른다.
- **컨벤션이 없으면 최소 형태로**: §1·§2 원칙만 적용하고, 새 폴더 구조나 템플릿을 강제하지 않는다.
- **상류/미러 문서는 직접 수정 전 소유권 확인**: 프로젝트에 소유권 표(예: `00-PROVENANCE.md`)가 있으면, 그 문서가 이 저장소 정본인지 상류 미러본인지 먼저 확인한다.

## 체크리스트 (execute 시작 전)

```
§1 결정 기록
[ ] 되돌리기 어려운 결정에 근거를 남겼는가?
[ ] 기록 위치가 프로젝트 컨벤션(docs/adr, 00-DECISIONS.md 등)과 일치하는가?

§2 드리프트 처리
[ ] 문서-코드 불일치를 발견하면 판정했는가?
[ ] 판정을 기록(문서 수정 또는 드리프트 로그)으로 남겼는가?

§3 기존 컨벤션 우선
[ ] 프로젝트 기존 문서 컨벤션을 확인했는가?
[ ] 컨벤션 없이 새 구조를 임의로 만들지 않았는가?
```
