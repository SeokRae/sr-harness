# execute

구현 시작 전 karpathy 체크포인트를 통과해야 한다.
단계별로 실행하고, 각 단계가 끝나면 verify 후 다음으로 넘어간다.

## 전제 조건 (브랜치 확인)

feature 브랜치에 있는지 확인한다. main이면 → `issue`로 돌아가서 브랜치 생성.

```bash
git branch --show-current  # feature/* 여야 함, main이면 안 됨
```

"실행 방식 판단"에서 작업자나 클라우드에 맡기기로 정하면, 이 확인은 맡은 작업자가 자기 작업 위치에서 한다.

## 시작 전 체크포인트 (karpathy §1 Think Before Coding)

다음을 확인하고 넘어간다:

```
[ ] 요청이 명확한가? → 불명확하면 먼저 질문
[ ] 여러 해석이 가능한가? → 모두 제시하고 선택받기
[ ] 더 단순한 방법이 있는가? → 있으면 먼저 제안
[ ] 성공 기준이 정의되어 있는가? → plan의 verify 기준 확인
```

코드 프로젝트인 경우 → `dev-coding-principles` 스킬을 로드하고 원칙(§1 Naming, §2 Exception Handling, §3 Test)을 구현에 적용한다.
코드 프로젝트인 경우 → `dev-architecture` 스킬을 로드하고 아키텍처 원칙(§1 Hexagonal, §2 Layer Separation, §3 Package Structure)을 구현에 적용한다.

문서를 작성·수정하는 태스크이거나 되돌리기 어려운 설계 결정을 포함하는 태스크인 경우 → `dev-documentation-principles` 스킬을 로드하고 문서화 원칙(§1 결정 기록, §2 드리프트 처리, §3 기존 컨벤션 우선)을 구현에 적용한다.

이상탐지·급증(spike) 모니터링 대시보드/리포트를 만드는 태스크인 경우 → `dev-monitoring-design` 스킬을 로드하고 정보설계 원칙(§1 측정, §2 진단, §3 탐지, §4 표현)을 구현에 적용한다.

코드 프로젝트인 경우 → 프로젝트 스택을 자동 감지한다:
```bash
ls build.gradle pom.xml 2>/dev/null
```
- `build.gradle` 또는 `pom.xml` 존재 → `dev-stack-java` 스킬을 로드하고 Spring Boot 관용구(§1 Spring Boot, §2 JPA, §3 Exception & Response)를 구현에 적용한다.

## 실행 방식 판단 (#151)

작업을 어디서, 몇 개로 나눠 돌릴지 정한다. 메인 세션과 오케스트레이터 작업자가 같은 표를 쓴다. 위에서부터 처음 맞는 행을 고른다.

| # | 조건 | 실행 방식 | 진입 조건 (없으면) | 금지 |
|---|------|----------|-------------------|------|
| 1 | 사용자 승인, 화면 확인, 확인 창이 필요하다 | Herdr 작업자 (보이는 pane) | `$HC_TERMINAL_ID`와 `herdr-delegate` 스킬 (없으면 직접 처리) | 클라우드, 예약 실행, 숨긴 터미널 |
| 2 | 다른 저장소에 쓴다 | 그 저장소를 cwd로 둔 작업자 | Herdr (없으면 그 저장소에서 세션을 열라고 안내하고 멈춘다) | 지금 세션에서 직접 쓰기 |
| 3 | 끝이 따로 정해지는 하위 작업(이슈 1개, PR 1개)이 2개 이상이고, 순서나 병렬 관계가 있다 | 오케스트레이터 작업자 1개 + 서브 작업자 | Herdr (없으면 아래 "서브에이전트 모드 판단") | 메인 세션이 서브 작업자를 직접 띄우기 |
| 4 | 특정 머신에서만 된다 | 그 머신의 작업자 (`hc run --on <machine>`) | `hc machine ls`에 그 머신이 있다 (없으면 알리고 멈춘다) | 다른 머신에서 대신 실행 |
| 5 | 오래 걸리고 무인이어도 된다 | 클라우드 세션이나 예약 실행 | 원격에 push된 상태, 로컬 전용 자원 불필요, 실행 전 사용자 승인 | 머지, 릴리즈, 승인이 필요한 단계 |
| 6 | 그 밖 | 직접 처리나 서브에이전트 (아래 "서브에이전트 모드 판단") | 없음 | 없음 |

- 2, 3, 4행은 겹치면 합친다. 예: 다른 저장소에 하위 작업이 여럿이면, 그 저장소를 cwd로 둔 오케스트레이터
- 1행이 맞으면 5행은 고르지 않는다
- 팀원끼리 대화가 필요하면 Claude Code 팀모드를 쓴다. 팀원 pane은 tmux 안에서만 뜬다. 못 쓰면 서브에이전트로 처리한다

### 역할

| 역할 | 하는 일 | 하지 않는 일 |
|------|--------|-------------|
| 메인 세션 | 작업자를 열고 정의(목표, 범위, 완료 조건, 산출 형식)만 쓴다. 통보를 받는다. 사용자 지시를 작업자에게 넘긴다 | 조사, 구현, 서브 작업자 띄우기 |
| 오케스트레이터 작업자 | 하위 작업을 나누고 이 표로 방식을 정한다. 서브 작업자를 띄운다. 결과를 모아 결과 파일 하나로 쓴다. 하나가 끝나면 목록의 다음 하위 작업을 이어 간다. 통보를 올린다 | 서브 작업자에게 맡긴 워킹트리에 쓰기 |
| 서브 작업자 | 하위 작업 하나(이슈 1개, 브랜치 1개, PR 1개)를 자기 worktree에서 처리하고 결과 파일을 쓴다 | 다른 작업자 띄우기. 서브에이전트와 팀모드는 쓸 수 있다 |

### 통보

오케스트레이터가 메인 세션에 올리는 통보는 네 가지다. 한 줄 형식은 `<종류> <run-id>/<name> <내용>`이다.

| 종류 | 내용 |
|------|------|
| 시작 | 작업 위치 |
| 확인 필요 | 터미널 주소(pane)와 질문 한 줄 |
| 완료 | 결과 파일 경로 |
| 실패 | 원인 한 줄, 결과 파일 경로 (있으면) |

전달 수단은 실행 방식 스킬(Herdr면 `herdr-delegate`)이 정한다.

### 공통 규칙

- 서브 작업자도 보이는 pane으로 띄운다. 숨긴 터미널로 띄우지 않는다
- 서브 작업자가 확인 창에서 멈추면, 오케스트레이터는 대신 답하지 않고 "확인 필요"를 올린다
- 한 세션이 동시에 띄우는 작업자는 3개까지다
- 작업자 비용은 결과로 받을 수 없어 금액 상한을 두지 않는다. 대신 작업자 수 상한을 지키고, 서브 작업자는 sonnet을 기본으로 쓴다
- 클라우드와 예약 실행은 실행 전에 사용자 승인을 받는다
- 한 워킹트리에 쓰는 작업자는 하나다. 서브 작업자는 `git worktree add`로 나눈 경로를 cwd로 받는다

## 서브에이전트 모드 판단

실행 방식 판단에서 직접 처리나 서브에이전트로 정해지면 이 절로 모드를 고른다. 작업자도 자기 작업 안에서 이 절을 쓴다.

플랜 파일(`.claude/session-plan.md`)을 읽어 제외 조건을 체크한다.

```
제외 조건 중 하나라도 해당 → 단일 / 순차 서브에이전트 모드
해당 없음                  → 병렬 서브에이전트 모드 (병렬 dispatch 기본)
```

제외 조건:
❌ 태스크 수 ≤ 2
❌ 동일 파일을 여러 태스크가 수정
❌ B가 A의 결과에 의존 (순차 의존성)
❌ 설계·판단·컨텍스트 공유가 필요한 작업

## 단일 실행 모드

태스크 수 < 3이고 단일 파일/모듈에 집중된 경우 이 모드로 실행한다.

## 구현 원칙 (각 단계마다 적용)

### karpathy §2 Simplicity First
코드를 작성하기 전:
- 요청한 것만 만든다 — 추가 기능, 미래 대비 추상화 금지
- 200줄로 쓸 수 있는 걸 50줄로 쓸 수 있으면 → 50줄로 쓴다

### karpathy §3 Surgical Changes
기존 코드를 수정할 때:
- 수정 대상 파일을 먼저 읽는다 (Read before Write)
- 값의 의미·범위가 바뀌는 변경(null 도입, 타입 변경, 기본값 변경 등)은 그 값의 소비처(호출부, 생성자, 파라미터)까지 추적한다 — 확인 방법은 언어마다 다름
- 요청과 직접 관련된 줄만 변경한다
- 주변 코드, 주석, 포맷은 건드리지 않는다
- 내 변경으로 생긴 unused import/변수만 제거한다 (기존 dead code 건드리지 않음)

### karpathy §4 Goal-Driven Execution
각 단계 실행 형식:
```
[Step N 실행 중]: {설명}
→ verify: {확인 방법}
→ 결과: ✅ 통과 / ❌ 실패 (실패 시 debug 전환)
```

## 결정 기록 (#129)

구현 중 후보가 둘 이상인 선택을 하면 `.claude/session-plan.md`의 `## Decisions` 절에 한 줄 남긴다. 절이 없으면 만든다.

```markdown
- D-{번호} {무엇을 정했나}: {고른 것} | 이유: {한 줄} | 제안: 사람|AI, 결정: 사람|AI
```

- 대상: plan과 Issue에 없던 선택. 라이브러리, 자료구조, 예외 처리, 기본값, 요구사항의 해석이 여기에 든다. plan에 이미 적힌 것과 이름 짓기 같은 사소한 선택은 적지 않는다
- `결정: 사람`은 사용자가 대화에서 직접 고른 경우만 쓴다. 사용자에게 묻지 않고 고른 것은 `결정: AI`다
- 앞선 결정을 뒤집으면 줄을 지우지 않는다. 옛 줄 끝에 `→ D-{새 번호}로 바뀜`을 붙이고, 새 줄에 바꾼 이유를 적는다
- 서브에이전트를 쓰는 모드에서는 서브에이전트가 결과에 고른 선택을 같은 형식으로 돌려주고, 이 세션이 `## Decisions`에 옮긴다

submit이 이 절을 PR 본문 "결정" 절로 옮긴다.

## 단계 간 커밋

각 논리적 단위 완료 시 커밋:
```bash
git add {관련 파일만}
git commit -m "{type}: {설명} (#N)"
```

**`git add .` 사용 금지** — 관련 파일만 개별 지정한다.

**커밋 단위**: `plan`의 단계 하나에서 verify를 통과한 변경이 커밋 하나다.
- verify를 통과하기 전에 커밋하지 않는다
- 여러 step을 한 커밋에 묶지 않는다
- 커밋 후에 다음 step으로 넘어간다

## 병렬 서브에이전트 모드

제외 조건이 없을 때 기본으로 시도하는 병렬 실행 모드.
Agent 툴로 독립 태스크를 병렬 dispatch한다.

다중 에이전트를 동시에 돌리기 전 `ownership-principles`(§3 오케스트레이션 세금)를 확인한다 — 결과를 전부 검토할 수 있는 규모인지 판단한 뒤 dispatch 수를 정한다.

### 원칙

- 독립 태스크를 Agent 툴로 병렬 dispatch — 단일 메시지에 여러 Agent 호출
- 각 에이전트는 focused/self-contained 프롬프트를 받아 독립 실행
- 에이전트 완료 후 결과를 리뷰하고 통합

### 실행 흐름

```
1. 플랜 파일에서 독립 태스크 목록 추출
2. 태스크별 에이전트 프롬프트 작성 (아래 형식)
3. Agent 툴로 병렬 dispatch (한 메시지에 모든 에이전트)
     - mode: "bypassPermissions" 또는 태스크 성격에 맞게
     - model: 모델 선택 기준표 참조
     - isolation: "worktree" (코드 프로젝트) — 충돌 방지
4. 에이전트 결과 수신 → 2단계 리뷰
     [태스크 N] 스펙 리뷰: 불일치 → 재dispatch
     [태스크 N] 코드 품질 리뷰: 이슈 → 재dispatch
5. 모든 리뷰 통과 → analyze → verify → submit
```

### 에이전트 프롬프트 형식

Agent 호출 시 prompt에 포함할 내용:
- 태스크 제목과 상세 설명
- 작업 대상 파일 경로
- 브랜치명, 이슈 번호
- 커밋 규칙 (위 "단계 간 커밋" 절: 관련 파일만 경로를 지정해 add, `#이슈번호` 포함)
- 성공 기준
- 구현 중 고른 선택을 결정 기록 형식으로 결과에 포함하라는 요청

### 충돌 방지 규칙

- 코드 프로젝트: `isolation: "worktree"` 사용 — 에이전트별 독립 worktree 자동 생성
- Vault 프로젝트: 동일 파일 수정 태스크는 순차 모드로 전환
- 모든 커밋에 이슈 번호 포함: `feat: 설명 (#이슈번호)`

### 모델 선택 기준

| 태스크 유형 | 모델 |
|------------|------|
| 단순 구현 (1~2 파일, 명확한 스펙) | haiku (빠르고 저렴) |
| 멀티파일 통합, 패턴 매칭 | sonnet |
| 아키텍처 판단, 리뷰 | opus |

## 순차 서브에이전트 모드

제외 조건이 해당되어 태스크를 순차적으로 처리해야 하는 경우.

### 원칙

- 동일 feature 브랜치 + 순차 dispatch → PR 충돌 없음 (코드 프로젝트는 동일 worktree에서)
- 각 태스크 완료 후 2단계 리뷰(스펙 → 코드 품질) 통과 시 다음 태스크 진행

### 실행 흐름

```
1. 플랜 파일에서 태스크 전문(全文) 추출
2. [태스크 N] 구현 서브에이전트 dispatch (순차)
     컨텍스트: 태스크 전문 + 관련 파일 경로 + 브랜치명 + worktree 경로
     서브에이전트 결과: DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED
3. [태스크 N] 스펙 리뷰 서브에이전트 dispatch
     ❌ 불일치 → 구현 서브에이전트 재dispatch → 재리뷰
     ✅ 통과 →
4. [태스크 N] 코드 품질 리뷰 서브에이전트 dispatch
     ❌ 이슈 → 구현 서브에이전트 재dispatch → 재리뷰
     ✅ 통과 → 다음 태스크
5. 모든 태스크 완료 → analyze → verify → submit
```

### 서브에이전트 상태 처리

| 상태 | 처리 |
|------|------|
| `DONE` | 스펙 리뷰로 진행 |
| `DONE_WITH_CONCERNS` | concerns 확인 후 스펙 리뷰 진행 |
| `NEEDS_CONTEXT` | 누락 컨텍스트 제공 후 재dispatch |
| `BLOCKED` | 원인 파악 → 컨텍스트 보강 재시도 / 더 강한 모델 / 태스크 분할 / 사용자 에스컬레이션 |

### 충돌 방지 규칙 (서브에이전트에게 명시 전달)

- 코드 프로젝트: 모든 파일 수정은 전달받은 worktree 경로 안에서 한다. main 워크트리 파일은 고치지 않는다
- Vault 프로젝트: feature 브랜치에서 직접 수정 (worktree 없음)
- 커밋은 "단계 간 커밋" 절 규칙대로 태스크 관련 파일만 경로를 지정해 add한다
- 커밋 전 `git pull --rebase origin {브랜치명}` 실행
- 모든 커밋에 이슈 번호 포함: `feat: 설명 (#이슈번호)`
- 구현을 마치면 커밋까지 하고 종료한다

### 모델 선택 기준

| 태스크 유형 | 모델 |
|------------|------|
| 단순 구현 (1~2 파일, 명확한 스펙) | haiku (빠르고 저렴) |
| 멀티파일 통합, 패턴 매칭 | sonnet |
| 아키텍처 판단, 리뷰 | opus |

## 완료 조건

**단일 모드**: plan의 모든 단계 verify 통과 → `analyze` 호출 (정합성 게이트 → verify → submit)
**병렬 서브에이전트 모드**: 모든 에이전트 완료 + 2단계 리뷰 통과 → `analyze` 호출 → verify → submit (PR 1개)
**순차 서브에이전트 모드**: 모든 태스크 2단계 리뷰 통과 → `analyze` 호출 → verify → submit (PR 1개)

세 모드 모두 `analyze` 판정은 구현 맥락이 없는 새 에이전트가 하고(analyze의 "실행 주체" 절), verify부터는 이 세션이 이어서 실행한다. 단일 모드도 예외가 아니다. 구현한 세션이 자기 diff를 판정하게 되는 모드라서 이 위임이 가장 필요하다.

## 예외 상황

- 테스트 실패 / 예상 밖 에러 → `debug` 전환
- 범위 밖 작업 발견 → session-plan.md Deviations 기록, 현재 작업 계속
- 서브에이전트 BLOCKED → 원인 분석: 컨텍스트 보강 재시도 / 모델 업그레이드 / 태스크 분할 / 사용자 에스컬레이션
