# dev-monitoring-design

이상탐지·급증(spike) 모니터링 화면(대시보드·리포트)을 설계하기 전, 각 섹션의 원칙을 확인하고 구현에 반영한다.
"무엇을 세는가 → 무엇이 원인인가 → 언제 이상인가 → 어떻게 보여주는가"의 4단계로 검증한다.

> **활성화 방법**: 프로젝트 `CLAUDE.md`에 아래 한 줄을 추가하거나, 이상탐지·급증·모니터링 대시보드/리포트를 만드는 태스크에서 로드한다.
> ```
> execute 실행 시 `dev-monitoring-design` 스킬을 로드하고 이상탐지 정보설계 원칙을 구현에 적용한다.
> ```
>
> **적용 대상**: 거절률/승인율, 에러율, 처리량, 지연 등 "지표가 평소 대비 얼마나 튀었나"를 판정하고 원인을 좁히는 모든 화면.

## §1 측정 — 무엇을 세는가 (지표의 정체)

**목표**: 비교하는 숫자가 실제로 답하려는 질문과 일치한다.

- **분포율 ≠ 실패율 ≠ 볼륨 (분모의 함정)**: "실패 중 이 사유의 비중"(분포율)과 "시도 대비 이 사유의 실패율"은 다른 지표다. "장애/이슈" 판단은 대개 시도 대비 실패율을 뜻한다. 분포율만 보면 시도량이 함께 늘 때 장애를 놓친다 → **분자(절대 건수)와 분모(시도 수)를 항상 함께 노출**한다.
- **조성 정합제약 → 기계적 희석 (compositional closure)**: 비중은 합=100%로 닫혀 있어, 한 항목이 급증하면 다른 항목이 **원인 없이** 하락한다(큰 음수 변화). 이 음수는 결과지 원인이 아니다 → 희석 방향(감소)에 "타 항목 급증의 산술적 결과" 주석/툴팁을 단다.
- **가산(%p) vs 승산(배수)**: 저base(0.8%→5.5%)는 +4.7%p로 작아 보여도 ~7배다. 신규 오류는 저base에서 시작하므로, 절대 임계(%p)만 쓰면 신규·희소 급증을 흘려보낸다 → 배수·비율 변화도 함께 판정한다.

## §2 진단 — 무엇이 원인인가 (WHERE ≠ WHY)

**목표**: "어디서 튀었나"에서 멈추지 않고 "왜"로 좁힌다.

- **코드 = 증상, 원인 아님**: 에러코드/사유코드는 조사 시작점이다. "원인 카드" 같은 네이밍이 코드=원인으로 오인시키지 않게 한다.
- **크기순 나열보다 기여율**: "이 사유가 이번 변화의 X%를 설명"이라는 **기여도(유의성) 랭킹**이 단순 Δ 크기순 top-N보다 원인 지목에 가깝고 오탐이 적다. 가능하면 외부 맥락(공지·휴일·릴리즈)을 주석으로 붙인다.
- **코드 ≠ 성질 (flat ≠ 클래스)**: 사유를 하나의 지표로 평평하게 세우면 성질(일시/영구·심각도·대응주체)이 사라진다. 같은 크기의 변화라도 정반대 액션일 수 있다 → 클래스(예: soft/hard, 자금/사기/인프라)와 대응주체(owner)를 축으로 얹는다.
- **세그먼트 드릴다운 + 심슨의 역설**: 집계 지표는 국소 급증을 대량 정상 트래픽에 감춘다. 상류 차원(발급사·BIN·노드·지역 등)으로 쪼개 "이 값으로 파고들기"를 제공한다. 집계 "정상"을 전 구간 안전으로 신뢰하지 않는다.

## §3 탐지 — 언제 이상인가 (기준선·임계)

**목표**: "정상 범위"를 데이터로 정의하고, 노이즈를 신호로 오인하지 않는다.

- **기준선: rolling window + 계절성**: baseline은 과거 rolling window로 잡되 주간/요일·월말 등 계절 패턴에 맞춘다. 기준일 요일 ≠ baseline 요일이면 가짜 변화가 생긴다. 창이 짧으면 노이즈, 길면 지연·오염(진행 중 이슈가 baseline에 흡수).
- **순간 급증 vs drift → 다중창(multiwindow)**: 짧은 창(현재성)과 긴 창(지속성)을 **AND로 결합**해 "어제만 튐"과 "며칠 점증(drift)"을 구분한다. 색·모양뿐 아니라 명시 라벨/배지로 확정한다. drift는 baseline에 섞여 변화량이 작아지므로 놓치기 쉽다.
- **다중비교 노이즈 게이트**: 수십 개 항목 × 매일 검정하면 우연히 임계를 넘는 항목이 반드시 생긴다(독립 20개면 최소 1개 위양성 확률 64%). **최소 발생건수 하한 + 지속성(N일 이상) 또는 σ 보정 임계**로 판정 문턱을 세운다.
- **관리한계(mean±kσ) vs 고정 임계**: 항목별 정상 변동폭이 다르므로 고정 임계는 요동 큰 항목을 과탐, 안정 항목을 과소탐한다. z-score/관리한계가 대안. (SPC 3σ 관습)

## §4 표현 — 어떻게 보여주는가 (인지·시각화)

**목표**: 결론이 먼저 보이고, 신호가 크기가 아니라 변화에 실린다.

- **판정 우선 + 점진적 공개 (verdict-first)**: "overview first → zoom/filter → details-on-demand"(Shneiderman). 최상단에 정상/이상 판정, 그다음 추세, 그다음 크기/원인. 정상일 때 하위 층은 접는다. 층을 쌓되(예: L1 판정배너 → L2 추세 히트맵 → L3 변화 다이버징) 한 뷰에 모든 걸 밀어넣지 않는다.
- **변화를 강한 채널에 (pre-attentive)**: 신호는 절대 크기가 아니라 변화(Δ)다. 크기를 가장 강한 시각 채널(길이·위치)에 두면 압도 항목이 화면을 지배한다 → 변화량을 강한 채널에 싣는다. (그래픽 지각 정확도: position > length > angle > area)
- **diverging은 0을 정중앙에**: 증가/감소를 0 기준 좌우로 분리하고, 중앙선이 무엇(zero/target/평균)인지 라벨한다. 값 순으로 정렬해 패턴을 노출한다.
- **이중부호화 + 색맹 안전**: 방향/상태를 hue 하나에만 싣지 않는다(적록색맹 ~8%). 위치·기호로 이중부호화하고, red/green 대신 **blue/orange** 계열을 쓴다.
- **행별 정규화엔 범례**: 히트맵을 행별 정규화하면 시간 형태는 보이나 "진함 = 절대 비중"이 아니다 → "진한 셀 ≠ 크기" 범례를 명시한다.
- **층간 임계 동기화**: 판정 배너의 "이상" 기준선과 차트의 가이드선이 **같은 상수**를 참조하게 한다. 배너는 "이상"인데 차트엔 넘은 항목이 없으면 신뢰가 깨진다.

## 체크리스트 (execute 시작 전)

```
§1 측정
[ ] 비교 지표가 답하려는 질문과 일치하는가? (분포율 vs 실패율 vs 볼륨)
[ ] 분자(건수)와 분모(시도)를 함께 노출하는가?
[ ] 비중 감소를 "개선"으로 오독할 여지(기계적 희석)를 주석으로 막았는가?
[ ] 저base 급증을 %p뿐 아니라 배수로도 판정하는가?

§2 진단
[ ] 코드/사유를 원인이 아니라 조사 시작점으로 다루는가?
[ ] 크기순이 아니라 기여율(변화의 X% 설명)로 원인을 제시하는가?
[ ] 항목의 성질(클래스·심각도·대응주체)을 축으로 얹었는가?
[ ] 세그먼트 드릴다운 경로가 있는가? (집계가 국소 급증을 감추지 않는가)

§3 탐지
[ ] baseline이 계절성/요일에 맞춰져 있는가?
[ ] 순간 급증과 drift를 다중창으로 구분하는가?
[ ] 최소 건수 + 지속성/σ 보정으로 노이즈 게이트를 두었는가?

§4 표현
[ ] 판정이 최상단이고 정상 시 하위 층이 접히는가?
[ ] 변화(Δ)가 크기가 아니라 강한 시각 채널에 실려 있는가?
[ ] diverging 0 중앙·색맹 안전·이중부호화·범례가 갖춰졌는가?
[ ] 판정 배너와 차트 가이드선이 같은 임계 상수를 참조하는가?
```
