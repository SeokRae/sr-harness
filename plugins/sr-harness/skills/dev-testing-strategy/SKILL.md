# dev-testing-strategy

Spring 통합 테스트를 작성하기 전, 각 섹션의 원칙을 확인하고 구현에 반영한다. `dev-coding-principles §3 Test`가 "단위냐 통합이냐"를 가른다면, 이 스킬은 "통합이라면 컨텍스트를 어떻게 띄우나"를 가른다.

> **활성화 방법**: 프로젝트 `CLAUDE.md`에 아래 한 줄을 추가한다.
> ```
> execute 실행 시 `dev-testing-strategy` 스킬을 로드하고 Spring 테스트 컨텍스트 구성 전략을 구현에 적용한다.
> ```

## §1 컨텍스트 구성 방식 — Runner vs Autowired

**목표**: 컨텍스트를 어떻게 띄울지 습관이 아니라 신호로 판단한다.

아래 세 신호 중 **하나라도 해당하면** `ApplicationContextRunner`(프로그래밍 방식). 셋 다 아니면 `@ExtendWith(SpringExtension.class)` + `@ContextConfiguration`/`@SpringBootTest(classes=...)` + `@Autowired`로 클래스당 컨텍스트 하나만 띄운다.

- **신호 1 — 프로퍼티 조합이 테스트 메서드마다 다르다**: 필수값 누락 시 기동 실패를 검증하거나, 메서드별로 다른 프로파일/프로퍼티를 쓴다. `@Autowired`는 클래스당 컨텍스트 하나가 전제라 실패 시나리오를 예외 없이 우아하게 받을 수 없다(컨텍스트 준비 단계에서 바로 에러가 터진다).
- **신호 2 — `AutoConfigurations.of(...)`로 여러 자동설정을 조합한다**: 자동설정끼리는 `@AutoConfigureAfter` 등으로 순서가 정해져 있다. `@ContextConfiguration(classes=...)`는 선언 순서로만 처리해 이 보장이 깨진다 — 특히 `BeanPostProcessor`를 등록하는 자동설정이 얽히면 조용히 깨진다(컴파일도 되고 다른 단언도 다 통과하는데 특정 값 하나만 예상과 달라지는 식이라 알아채기 어렵다).
- **신호 3 — 컨텍스트 구조 자체가 단언 대상이다**: 빈의 존재/부재, 두 빈이 같은 인스턴스인지, 기동 성공/실패 — 이런 건 `@Autowired`로 표현할 방법이 없다. 주입할 대상이 "없어야 정상"인 케이스를 우아하게 확인할 수 없고, 컨텍스트가 실패하면 테스트 메서드가 실행되기도 전에 셋업 단계에서 예외가 터진다.

```java
// 신호 3 예시 — 이 이름의 빈이 없어야 정상인 케이스
contextRunner.run(context -> {
    assertThat(context).hasNotFailed();
    assertThat(context).doesNotHaveBean("sharedHttpClient");
    assertThat(context).hasBean("dedicatedHttpClient");
});
```

**주의**: 신호 1(프로퍼티 공유 여부)만 기계적으로 확인하고 판단하지 않는다. 프로퍼티는 완전히 고정 공유하는데 신호 3에 걸려 있는 테스트를 신호 1만 보고 `@Autowired`로 옮기면 조용히 잘못된 선택이 된다.

## §2 컨텍스트 스코프 — 좁힘이 기본, 전체는 예외적으로

**목표**: 검증 대상과 무관한 의존성(DB, 메시징 등)을 매번 끌고 오지 않는다.

- **기본값은 좁힌 컨텍스트**: 검증 대상 빈 + 필요한 설정 빈만 `@Configuration` + `@Import`로 최소 구성한다. `@SpringBootTest`(전체 자동설정 포함)를 통합 테스트의 기본값으로 쓰지 않는다.
- **전체 컨텍스트는 두 역할로만 한정한다**:
  - **스모크**: `contextLoads()`류 — 본문이 비어 있고, 빈 정의 충돌·순환 의존·필수 프로퍼티 누락처럼 "아예 안 뜨는" 문제만 잡는다. 프로젝트당 1개로 충분하다. 도메인이 늘어난다고 이 계층의 테스트를 늘리지 않는다.
  - **E2E**: 여러 레이어가 실제로 맞물려 동작하는지 확인해야 할 때만 만든다. 이 계층이 필요하다는 신호는 "검증 대상이 한 조각의 배선이 아니라 여러 조각의 상호작용"이라는 점이다.
- **좁힌 테스트와 전체 테스트는 서로 다른 결함을 잡는다**: 좁힌 테스트는 특정 조각의 세부 동작 회귀(예: 메트릭 트래커가 실제로 배선됐는가)를 잡고, 전체 테스트는 "합쳤을 때만 드러나는 충돌"을 잡는다. 본문이 빈 스모크 테스트는 전자를 구조적으로 못 잡는다 — 예외 없이 뜨기만 하면 통과하기 때문이다. 하나가 있다고 다른 하나가 불필요해지지 않는다.

## §3 프로퍼티 값 관리 — 실제 설정을 그대로 로드한다

**목표**: 운영 설정이 바뀌었을 때 테스트가 조용히 뒤처지지 않는다.

- **하드코딩 금지**: URI, 타임아웃, 재시도 횟수처럼 이미 실제 yml/properties에 있는 값을 테스트 코드에 리터럴로 다시 적지 않는다. 실제 설정 파일을 그대로 로드해서 쓴다 — 운영 값이 바뀌면 테스트도 자동으로 따라가야 한다.
- **`@DynamicPropertySource`는 런타임에만 정해지는 값 전용**: 스텁 서버 포트, Testcontainers가 뜬 뒤에만 알 수 있는 접속 정보처럼 미리 알 수 없는 값에만 쓴다. 이미 설정 파일에 있는 값을 여기서 다시 적으면 하드코딩과 같은 문제가 재발한다.
- **정적 메서드 실행 시점을 기억한다**: `@DynamicPropertySource` static 메서드는 컨텍스트 리프레시 **전에** 실행된다 — 그 시점엔 `@Autowired`로 다른 설정값을 읽을 수 없다. 정확한 값이 필요하면(예: 요청 경로) 컨텍스트가 뜬 뒤 `@Autowired`로 실제 설정을 읽어 기대값을 계산하거나, 값에 의존하지 않는 catch-all 방식으로 설계한다.

## 체크리스트 (통합 테스트 작성 전)

```
§1 컨텍스트 구성 방식
[ ] 프로퍼티 조합이 테스트 메서드마다 다른가? (다르면 Runner)
[ ] AutoConfigurations.of(...)로 여러 자동설정을 조합하는가? (조합하면 Runner)
[ ] 빈 존재/부재, 기동 성공/실패 자체가 단언 대상인가? (그렇다면 Runner)
[ ] 셋 다 아니라면 @Autowired로 클래스당 컨텍스트 하나만 띄웠는가?

§2 컨텍스트 스코프
[ ] 검증 대상과 무관한 의존성을 끌고 오지 않았는가?
[ ] 전체 컨텍스트를 쓴다면 스모크/E2E 중 어느 역할인지 명확한가?

§3 프로퍼티 값 관리
[ ] 이미 설정 파일에 있는 값을 리터럴로 다시 적지 않았는가?
[ ] @DynamicPropertySource는 런타임에만 정해지는 값만 오버라이드하는가?
```
